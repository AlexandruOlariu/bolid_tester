# Plan 30 — Store release preparation (Play Store + App Store) and stability targets

**Size:** M code (1 day) + owner store-console work · **Depends on:** plan 08 (signed AAB, OTA,
privacy policy, `docs/release.md`), plan 09 (iOS build), plan 10 (Maestro), plan 11 (RO strings),
plan 31 (crash-free metric), plan 32 (feedback) · **Roadmap:** v1.0 "Play Store + App Store",
"Stability targets"

## Goal

Everything a store listing needs exists in the repo and is regenerated by scripts, the data-safety
answers are derived from what the code actually does, the rollout path (internal → closed →
production with staged percentages) is written down with go/no-go criteria, and the crash-free KPI
is defined and measured.

## Why (verified)

- Assets: `assets/icon.png`, `adaptive-icon.png`, `splash-icon.png` are all 1024 × 1024. Play needs
  a 512 × 512 hi-res icon (downscale) and a **1024 × 500 feature graphic** (missing). No screenshots
  exist anywhere in the repo.
- Android targets: React Native 0.85's version catalog (`node_modules/react-native/gradle/libs.versions.toml`)
  sets `targetSdk = 36`, `compileSdk = 36`, `minSdk = 24`; the Expo root-project plugin defaults to
  35 only when the catalog is absent. Google Play's 2026 requirement for new apps and updates is
  API 35 or higher — SDK 56 builds comply. Record the value in the release doc and re-verify at
  each SDK upgrade.
- `app.json`: `version 0.1.0`, `android.package com.bolidtester.app`, `ios.bundleIdentifier
com.bolidtester.app`, three Android permissions (`BLUETOOTH_SCAN`, `BLUETOOTH_CONNECT`,
  `ACCESS_FINE_LOCATION`), `react-native-ble-plx` plugin with `neverForLocation: true`;
  `expo-location` is a dependency (GPS trip tracks) so the fine-location permission is genuinely
  used, which the data-safety form must say.
- `eas.json` has `production: { autoIncrement: true }` and an empty `submit.production` — no store
  credentials configured.
- No `docs/privacy-policy.md` or `docs/release.md` yet (plan 08 deliverables); this plan extends them.

## Design

### 1. Store assets (`store/` at the repo root, committed)

```
store/
├── listing/en/{title.txt, short.txt (≤80), full.txt (≤4000), keywords.txt (iOS ≤100), whats-new/1.0.0.txt}
├── listing/ro/…                     # same files, Romanian (plan 11 glossary)
├── graphics/feature-graphic.png     # 1024 × 500 — brand green #2bb673 background, logo, "OBD2 diagnostics for any car"
├── graphics/icon-512.png            # generated from assets/icon.png
├── screenshots/android/phone/*.png  # 1080 × 2400, generated
├── screenshots/android/tablet-10/*.png  # 1600 × 2560 (plan 21 layouts)
├── screenshots/ios/6.7/*.png        # 1290 × 2796
└── README.md                        # how each file is produced; which are hand-made
```

`scripts/store-assets.mjs`: generate `icon-512.png` and resize screenshots with `sharp`
(devDependency) — the feature graphic is hand-made once (Figma/any tool) and committed.

Listing copy (EN), to be mirrored in RO:

- Title (≤ 30): `Bolid Tester – OBD2 Scanner`
- Short: `Read live data, fault codes, readiness & more from any OBD2 car over a Bluetooth LE ELM327.`
- Full: structure = what it does (generic OBD2 for any car) · features list (Tier A/B) · "Workshop
  tools for VAG cars are experimental and clearly marked" · what it is **not** (no VCDS replacement,
  no airbag/immobilizer, needs a BLE ELM327 adapter) · privacy sentence (local-first, no accounts)
  · supported adapters line. Reuse the README "Is / Is not" paragraphs verbatim where possible.
- What's new 1.0.0: five bullets from `docs/roadmap.md` v0.2–v0.7 highlights.

### 2. Screenshot automation (Maestro, simulator mode)

`.maestro/screenshots.yaml` (runs after plan 10's harness exists): launch with `clearState`, set
Settings → Developer → Simulator → Golf, inject `P2183,P2015`, then for each screen:
`tapOn` → `waitForAnimationToEnd` → `takeScreenshot: store/screenshots/android/phone/0N-<name>`.
Screens (8, in store order): Live dashboard (engine running sim), Faults with two codes + readiness,
Used-car inspection verdict, Charts two panels, Module scan (Golf sim), Trips with GPS map (plan v0.4
if present, else Battery), Maintenance log, Connect screen (BLE mode, first-run card). Run on an
emulator with the demo locale `en-US`, then `ro-RO` for the RO set. A `status bar demo mode`
command (`adb shell settings put global sysui_demo_allowed 1` + `am broadcast -a com.android.systemui.demo …`)
cleans the status bar — put both commands in `scripts/screenshots.sh`.

iOS screenshots: same flow on an iPhone 15 Pro Max simulator via `maestro` (plan 09 build).

### 3. Google Play Data safety — answers derived from the code

| Data type                             | Collected?                                                                                        | Shared?                                                     | Why / where                                                                                                                                                  |
| ------------------------------------- | ------------------------------------------------------------------------------------------------- | ----------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Location (precise)                    | **Yes, optional** — only while a trip is recorded with GPS on                                     | No                                                          | `expo-location` in `trackRecorder.ts`; stays on device; user can export                                                                                      |
| Personal info (name/email)            | No                                                                                                | No                                                          | No accounts                                                                                                                                                  |
| Device or other IDs                   | No (Bluetooth adapter MAC is stored on device for reconnect, never sent)                          | No                                                          | `sessionStore.deviceId`, `lastTarget`                                                                                                                        |
| App activity / diagnostics            | **Only if the user turns on crash reports** (plan 31): crash logs, scrubbed                       | **Yes, to the crash-reporting processor** when enabled      | Mark "Crash logs", "optional", "data is encrypted in transit", "user can request deletion" = No (not linkable) → answer per Play guidance for anonymous data |
| Vehicle data (VIN, DTCs, live values) | Stored on device; sent **only** to the user-configured AI server when the user taps Diagnose (AI) | Disclosed as "App functionality"; the server is user-chosen | `openaiClient.ts`; the form's "Other personal info" is not the right bucket — describe in the privacy policy and mark "data not collected" by the developer  |
| Files/exports                         | User-initiated share only                                                                         | No                                                          | `expo-sharing` hooks                                                                                                                                         |

Security practices: data encrypted in transit (HTTPS to update server; the AI server URL may be
plain HTTP on a LAN — say "where the user's server supports it"), no account deletion flow (none
needed), committed to Play Families? No. Declare the **Bluetooth** permission rationale and
**ACCESS_FINE_LOCATION** rationale ("trip GPS tracks; never used for Bluetooth scanning —
`neverForLocation`").

### 4. Apple privacy nutrition labels

"Data Not Linked to You": Precise Location (app functionality, optional), Crash Data (optional,
plan 31), Diagnostics (optional). Everything else: "Data Not Collected". Tracking: No. Add
`NSUserTrackingUsageDescription`? Not needed (no tracking). Export compliance: `ITSAppUsesNonExemptEncryption: false`
(plan 09). App category: Utilities (secondary: Productivity). Age rating 4+.

### 5. Content rating, categories, policy items

Play: IARC questionnaire → Everyone. Category: Auto & Vehicles. Target audience 18+ is **not**
required (no age-gated content) — pick 16+/18+ anyway to avoid Families policy. Play "App access":
no login; note that full functionality needs an OBD2 adapter and provide the simulator path for
reviewers ("Settings → Developer → Simulator") in the review notes. iOS review notes: same
simulator instructions + a 20-second screen recording of a BLE connection (owner records on the
Golf once).

### 6. Rollout and go/no-go

`docs/release.md` gets a "Store rollout" section:

1. **Internal testing** (Play) / **TestFlight internal** — every `v*` tag build; smoke = plan 10
   Maestro flow on the signed build + the `docs/testing.md` simulator checklist.
2. **Closed testing** (Play "Bolid testers" list, ≥ 12 testers for 14 days — Play's requirement for
   personal developer accounts created after Nov 2023) / **TestFlight external**. Exit criteria:
   crash-free sessions ≥ 99.5 % over the period (plan 31 release health; if telemetry is off for
   all testers, fall back to "zero fatal entries in collected feedback bundles"), no P0 bugs open.
3. **Production staged rollout**: 10 % → 50 % → 100 % with 48 h between steps; halt rule: crash-free
   < 99 % or any ANR cluster > 0.5 %. iOS: phased release on (7-day automatic).
4. Hotfix path: JS-only → OTA (`eas update --branch production`), native → new tag + expedited
   review request.

### 7. Stability KPI definition

`docs/release.md` § "Stability": metric = Sentry **crash-free sessions** (plan 31) per release;
targets v1.0: ≥ 99.5 % on Android, ≥ 99.5 % on iOS; secondary: Play Vitals user-perceived crash
rate < 1.09 % (Play's bad-behaviour threshold) and ANR rate < 0.47 %. Simulator path must be
crash-free in CI (plan 10 e2e nightly). Record per-release numbers in a table.

### 8. In-app pieces

- Settings → About: version/build, **Rate this app** (`Linking.openURL` to
  `market://details?id=com.bolidtester.app` / App Store URL), **Privacy policy**, **Report a
  problem** (plan 32), **Licences** (third-party notices — generate `docs/third-party-licenses.md`
  with `npx license-checker --production --markdown` in `scripts/licenses.mjs`; show inside the
  app as a scrollable text screen `/licenses`).
- `app.json`: `android.versionCode` managed by plan 08; `ios.buildNumber` by EAS `autoIncrement`;
  `expo.description`, `expo.privacy: 'public'`, `expo.githubUrl`.

## Steps

1. `store/` tree, EN/RO copy, `README.md`; `scripts/store-assets.mjs` (`sharp` devDep) for icon
   and resizing; hand-make the feature graphic.
2. `.maestro/screenshots.yaml` + `scripts/screenshots.sh`; generate the Android phone set from the
   simulator; commit.
3. Data-safety and nutrition-label answer sheets as `store/compliance/play-data-safety.md` and
   `store/compliance/apple-privacy.md` (the tables above, kept in sync with the privacy policy —
   add a test? Not mechanical; add a line to the plan 08 release checklist "re-read compliance
   sheets").
4. `docs/release.md` sections 6–7; About screen items; `/licenses` screen + script.
5. `eas.json` `submit.production`: `android.serviceAccountKeyPath` (path to a gitignored JSON),
   `android.track: internal`, `ios.appleId`/`ascAppId` placeholders documented (values are owner
   secrets, never committed).
6. `npm run ci`.
